# Account deletion and recovery-copy operations

This is a reviewable operational plan, not authorization to access production stores, purge data, change retention or contact providers. The implemented journal and local suppression planner protect code paths but do not prove that old Firestore, encrypted exports or provider copies were erased.

## Ownership and inventory gate

The owner must assign the operator and independent verifier, approve the exact read-only inventory targets, and establish the actual retention basis/window before any write is proposed. Keep the working inventory private. Record store/deployment identity, account ownership representation, capture time, access path, encryption/key owner, restore paths, current writer status and backup expiry controls. A public copy must contain only counts, opaque non-secret target labels and fingerprints, not credentials, object download URLs, account IDs or financial records.

| Copy class | Inventory required before action | Proposed disposition, subject to owner decision | Verification needed |
|---|---|---|---|
| Active Mongo and imported companions | Current runtime database identity and latest complete journal | Existing password-confirmed account deletion purges account-owned data; current journal remains separate | Root/owned/archived/email-claim absence, unchanged other owners, durable journal, account access rejected |
| Retained old Firestore | Exact old project/database, every `users/{uid}` descendant including missing parents, flat `userId`/`ownerId` rows, old writer deployments | Review exact account paths derived from immutable identity, then separately authorize scoped cleanup. Keep all stale writers disabled | Independent recursive readback, no matching account descendants/claims, unrelated owner counts/fingerprints preserved |
| Plaintext/decrypted and encrypted local exports | All original, copied, downloaded and staged files, key ownership and backup/sync copies | Owner selects lawful retention, controlled expiry or exact-file destruction. Do not rewrite an immutable snapshot pretending it never contained deleted data | Owner-approved file/backup inventory reconciliation, storage/key disposition receipt, remaining-copy reasons and expiry evidence |
| Backup-only static deployments/assets | Exact project/deployment/build output and whether another verified backup remains | Separately approved retirement or expiry only after required copies are preserved and accessible URLs/integrations are understood | Deployment/asset absence or access denial, destination backup receipt; never equate unguessable URL with deletion |
| Managed database/hosting backups | Actual plan, regions, snapshot schedule, retention/restore controls, service-provider terms | Owner defines the deletion/expiry process available under the actual service; keep suppressed identities inaccessible during any retained recovery period | Provider retention/control receipt and restore suppression test; no unsupported immediate-erasure claim |
| AI provider processing/security copies | Actual selected providers, account terms, controls and permitted regions | Apply documented provider deletion/request or expiry mechanisms where available. Do not invent a zero-retention setting or promise removal of required security records | Approved provider response or documented expiry basis, with retained reasons disclosed truthfully |

The request already starts durable `recoveryCleanup: pending`; users should not need a second request. There is no live inventory daemon or provider-deletion integration in this change. An operator must review pending requests through a separately authorized access path. Do not mark recovery cleanup complete based only on the active API's 204 response or this plan.

## Exact-target cleanup gate

1. Obtain separately approved read-only inventory. Preserve the latest journal outside any restored snapshot and verify complete history/currentness against the active service. Identify the deletion key using the immutable account ID privately, never by email alone.
2. Create a per-request target plan with the operator/verifier, exact store/path/object scope, ownership evidence, selected retention basis, retained exceptions and rollback consequences. Reused email claims owned by a new ID are excluded. Unknown ownership blocks that target.
3. Present that concrete plan and any script for separate mutation approval. Read the entire script and imported writers first. A script must emit an account-content-free dry-run receipt, refuse mismatched source/target/fingerprints, preserve unrelated owners, and be resumable after partial failure. No such production writer is provided here.
4. Execute only the approved exact targets. A reversible rollback must never resurrect a journaled account. If irreversible deletion is authorized, record that explicitly rather than claiming a rollback exists. Provider backup limitations or legal/security retention must be recorded as pending or retained exceptions with the actual basis.
5. Independently read back each approved target's absence/expiry/access controls and unchanged unrelated data. Store the receipt privately, publish only redacted counts/fingerprints, and retain the suppression key. Any unresolved copy keeps recovery cleanup pending.

Completion dates and retention windows remain owner decisions requiring actual provider/storage evidence. This document deliberately assigns none. A future reviewed completion handler must require evidence for every inventory target before changing `recoveryCleanup`; no automatic completion/expiry flag is implemented.

## Restore and rollback gate

1. Freeze restoration and all writers, including old previews/background jobs, or establish independently reviewed equivalent transactional fencing. Account deletion must not race an unguarded restore.
2. Preserve/export the latest complete journal from the current authoritative store outside the historical snapshot. An empty or older backup journal is insufficient. If complete latest history is unavailable, stop restoration of account records; do not silently assume there were no deletions.
3. Authenticate/decrypt the chosen historical snapshot locally using its independent source receipt. Use the local count-only `planRecoverySuppression.ts` with separately reviewed journal/source fingerprints. Resolve every ownership-review record and mapping conflict. No production import exists in this tool.
4. Implement and independently review a separate restore writer before authorizing it. Suppress every journaled immutable identity regardless of cleanup status, including roots, email claims, flat owned rows and archived/deeper descendants. Never overwrite the authoritative journal with snapshot history. Stale rate counters and migration markers are not account records to revive.
5. Test with synthetic fixtures: pre-deletion snapshot plus latest journal, absent root with orphan descendants, partial journal failure, concurrent writers, changed ownership, reused email/new identity, unknown rows, and interrupted restore. Verify normal login/read/write remains denied for restored journaled roots while password-confirmed deletion retry remains possible for locked roots.
6. Stage into an isolated destination. Independently verify counts and fingerprints after approved exclusions, latest-journal preservation, no suppressed identity/data, unchanged allowed owners, runtime indexes, JWT identity and deletion fences. Old-snapshot parity alone is not success. Production promotion remains separately authorized.

The current source adds a defense in depth: ordinary API/session access, account write fences and public-profile lookup reject identities present in the journal, even if an old unlocked root was incorrectly restored. That guard does not erase records accidentally restored by an external tool and cannot protect a whole-database restore that discards the journal. Preserve the journal and retain physical cleanup as a distinct operation.
